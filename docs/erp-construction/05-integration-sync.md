# 05 — الربط والمزامنة (Integration & Synchronization)

هذه الوثيقة تجيب على السؤال الأهم: **كيف تتحدث الأقسام مع بعضها دون أن تتحول إلى شبكة عنكبوتية غير قابلة للصيانة؟**

---

## 1. المبدأ: ثلاث قنوات ربط فقط

| القناة | متى تُستخدم | مثال | الاتساق |
|--------|-------------|------|---------|
| **استدعاء متزامن لواجهة نطاق** | حين يحتاج المستدعي جواباً فورياً لاتخاذ قرار | المشتريات تسأل التكاليف: "هل يوجد رصيد موازنة كافٍ؟" | فوري |
| **حدث نطاق (Domain Event)** | حين يجب إعلام الآخرين بما حدث دون انتظارهم | `GoodsReceived` → تُعلم المالية والتكاليف والمشروع | نهائي (ثوانٍ) |
| **نموذج قراءة (Read Model)** | حين يحتاج نطاق بيانات نطاق آخر للعرض فقط | شاشة المشروع تعرض اسم المورّد | نهائي |

**ممنوع منعاً باتاً:** استعلام SQL مباشر عبر مخططات النطاقات، أو مفتاح أجنبي عابر (عدا نحو النطاق المرجعي).

## 2. نمط الصندوق الصادر (Transactional Outbox)

المشكلة الكلاسيكية: نحفظ في قاعدة البيانات ثم ننشر حدثاً — إذا سقط النظام بينهما، ضاع الحدث وفقد النظام اتساقه.

**الحل المعتمد:**

```
┌─ معاملة قاعدة بيانات واحدة (ACID) ─────────────────────┐
│  1. INSERT INTO inventory.goods_receipt (...)          │
│  2. UPDATE inventory.stock_balance   (...)             │
│  3. INSERT INTO core.outbox (event_type, payload, ...) │
└────────────────────────────────────────────────────────┘
                        │ COMMIT
                        ▼
              ┌──────────────────┐
              │ ناشر الصندوق     │  يقرأ الأحداث غير المنشورة
              │ (Outbox Relay)   │  بترتيب، وينشرها للناقل
              └────────┬─────────┘
                       ▼
              ┌──────────────────┐
              │  ناقل الأحداث    │
              └────────┬─────────┘
        ┌──────────────┼──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
   التكاليف        المالية        المشاريع        الإشعارات
```

**ضمانات:**
- **التسليم مرة واحدة على الأقل** + **معالجة مرة واحدة فعلياً (Idempotent Consumers)** عبر جدول `processed_events (consumer, event_id)`.
- **حفظ الترتيب** لكل مفتاح تجميع (نفس المشروع/نفس الأصل) عبر `partition_key`.
- **طابور الرسائل الميتة (DLQ)** + إعادة محاولة تصاعدية + شاشة إدارة لإعادة التشغيل اليدوي.

**بنية الحدث الموحّدة:**
```json
{
  "event_id": "uuid",
  "event_type": "inventory.goods_received.v1",
  "occurred_at": "2026-08-27T10:15:00Z",
  "tenant_id": "uuid",
  "legal_entity_id": "uuid",
  "actor_id": "uuid",
  "correlation_id": "uuid",     // يربط كل أحداث عملية واحدة
  "causation_id": "uuid",        // الحدث الذي سبّب هذا الحدث
  "partition_key": "project:uuid",
  "version": 1,
  "payload": { }
}
```
> `correlation_id` هو ما يسمح بتتبع رحلة كاملة: من طلب الشراء حتى الدفع، عبر ستة أقسام، في شاشة واحدة.

## 4. العمليات الطويلة (Sagas) — أربع دورات حاكمة

### أ) دورة الشراء حتى الدفع (Procure-to-Pay)
```
طلب شراء ──▶ فحص الموازنة والمخزون ──▶ اعتماد (مصفوفة DoA)
   ──▶ طلب عروض ──▶ مقارنة فنية ومالية ──▶ ترسية واعتماد
   ──▶ أمر شراء (قيد التزام) ──▶ متابعة توريد
   ──▶ استلام GRN ──▶ فحص جودة ──▶ إدخال مخزن
   ──▶ فاتورة المورّد ──▶ مطابقة ثلاثية آلية
   ──▶ جدولة دفع ──▶ اعتماد صرف ──▶ سداد ──▶ إقفال
```
**نقاط التعويض (Compensation):** رفض الفحص ⇒ مرتجع للمورّد + عكس قيد الاستحقاق. إلغاء PO ⇒ عكس الالتزام.

### ب) دورة العمل حتى النقد (Work-to-Cash)
```
قياس الكميات في الموقع ──▶ اعتماد الجودة (IR)
   ──▶ اعتماد الاستشاري ──▶ إعداد المستخلص
   ──▶ خصم المحتجز والدفعة المقدمة والغرامات
   ──▶ اعتماد داخلي ──▶ تقديم للعميل
   ──▶ شهادة الدفع ──▶ فاتورة ضريبية إلكترونية
   ──▶ ذمم مدينة ──▶ متابعة تحصيل ──▶ قبض ──▶ تسوية
```

### ج) دورة البلاغ حتى الإغلاق (Request-to-Resolution) — الصيانة
```
بلاغ ──▶ تصنيف وأولوية ──▶ بدء مؤقت SLA
   ──▶ تخصيص فني ──▶ أمر عمل على الجوال
   ──▶ صرف قطع غيار ──▶ تنفيذ ──▶ توقيع المستفيد
   ──▶ تحقق الجودة ──▶ إيقاف SLA ──▶ فوترة ──▶ إغلاق
```

### د) دورة التوظيف حتى نهاية الخدمة (Hire-to-Retire)
```
طلب توظيف ──▶ اعتماد الملاك ──▶ استقطاب ──▶ مقابلات
   ──▶ عرض ──▶ تأشيرة وإجراءات ──▶ مباشرة
   ──▶ تخصيص لمشروع ──▶ حضور وتوزيع ساعات ──▶ رواتب
   ──▶ تقييم وترقية ──▶ نهاية خدمة ──▶ إخلاء طرف ──▶ تسوية
```

كل Saga تُدار بـ **Process Manager** يحفظ حالته في `workflow_instance`، ويتعامل مع المهلات (Timeouts) والتعويض، وكل خطوة قابلة لإعادة التشغيل.

## 5. مصفوفة ملكية البيانات (MDM Ownership)

**قاعدة:** لكل حقيقة **مالك واحد** يكتبها؛ الباقون يقرؤون نسخة منشورة.

| البيانات | المالك (الكاتب الوحيد) | المستهلكون (قراءة) |
|----------|------------------------|--------------------|
| بيانات الشريك (عميل/مورّد) | البيانات المرجعية | المشتريات، المالية، CRM، العقود |
| دليل الحسابات وأكواد الكلفة | المالية | كل النطاقات |
| هيكل WBS | المشاريع | التكاليف، المشتريات، المخازن، الجودة |
| ملف الموظف | الموارد البشرية | الرواتب، HSE، المشاريع، المعدات |
| فهرس الأصناف والأسعار | البيانات المرجعية | المشتريات، المخازن، التقدير |
| سجل المعدات | المعدات | المشاريع، الصيانة، الأصول الثابتة |
| رصيد المخزون | المخازن | المشتريات، المشاريع، المالية |
| قيمة العقد والتغييرات | العقود | المشاريع، التكاليف، المالية |
| أسعار الصرف | البيانات المرجعية | الكل |

**آلية المزامنة الداخلية:** `MasterDataChanged` ⇒ كل نطاق يحدّث نموذج قراءته المحلي (Projection). لا نطاق يستعلم جدول نطاق آخر مباشرة.

## 6. المزامنة الميدانية دون اتصال (Offline-First Sync)

المواقع الإنشائية غالباً بلا إنترنت مستقر. هذا ليس حالة استثنائية بل الوضع الطبيعي.

### ما يعمل دون اتصال (إلزامي)
التقرير اليومي · صرف واستلام المواد · قراءة عدادات المعدات · الحضور بـ GPS · طلبات الفحص وقوائم التحقق · عدم المطابقات وقائمة الملاحظات · الحوادث وتصاريح العمل · أوامر عمل الصيانة · الصور والتوقيعات · قياس الكميات.

### المعمارية
```
┌──────────────── جهاز الميدان ────────────────┐
│  واجهة التطبيق                                │
│      ▼                                        │
│  قاعدة محلية (SQLite / WatermelonDB)          │
│      ▼                                        │
│  طابور التغييرات المحلي (Mutation Queue)      │
│      ▼                                        │
│  محرك المزامنة  ──── حين يتوفر الاتصال ────▶  │
└───────────────────────────────────────────────┘
                        │
                        ▼
              ┌──────────────────────┐
              │ نقطة المزامنة (API)  │
              │  push  ثم  pull      │
              └──────────┬───────────┘
                         ▼
                  الخادم (مصدر الحقيقة)
```

### قواعد حل التعارض (Conflict Resolution)

| نوع البيانات | الاستراتيجية | مثال |
|--------------|--------------|------|
| **إضافة فقط (Append-only)** | لا تعارض أصلاً — كل السجلات تُقبل | التقارير اليومية، الصور، قراءات العدادات، الحوادث |
| **العدّادات/الأرصدة** | تُرسل **الحركة** لا الرصيد النهائي (Delta) | صرف 50 كيس إسمنت، لا "الرصيد صار 200" |
| **مستندات الحالة** | الخادم صاحب القرار + رفض مع سبب | أمر عمل أُغلق مركزياً بينما الفني يعدّله |
| **تعديل نفس الحقل** | آخر كتابة تفوز + سجل تعارض للمراجعة البشرية | تعديل ملاحظة من شخصين |
| **المستندات المعتمدة** | لا تُعدَّل محلياً إطلاقاً — قراءة فقط | مستخلص مُعتمد |

### تفاصيل تقنية حاسمة
- **معرّفات UUID تُولَّد على الجهاز** — لا انتظار للخادم، ولا تصادم.
- **مفتاح التكرار (Idempotency Key)** لكل عملية: إعادة الإرسال لا تُنشئ سجلاً مكرراً.
- **السحب التفاضلي (Delta Pull)** بـ `since_cursor` — لا تحميل كامل.
- **النطاق المحدود (Scoped Sync):** الجهاز يحمّل **مشاريعه فقط** — لا كامل قاعدة الشركة.
- **الصور:** رفع مؤجل بأولوية منخفضة، مضغوطة، مع استئناف بعد الانقطاع.
- **التوقيع الميداني:** يُخزَّن كصورة + بصمة زمنية + موقع GPS + معرّف الجهاز.
- **حد أقصى للعمل دون اتصال:** 14 يوماً ثم إجبار المزامنة (لمنع تراكم لا يُحل).

## 7. التكاملات الخارجية (External Integrations)

| النظام | الاتجاه | البروتوكول | ملاحظات |
|--------|---------|------------|---------|
| **الفوترة الإلكترونية** (زاتكا/الهيئة الضريبية) | صادر | REST + توقيع رقمي | إلزامي حسب الدولة، طابور إعادة محاولة |
| **البنوك** | ثنائي | ملفات ISO 20022 / SFTP / API | تحويل رواتب، كشوف، تسوية آلية |
| **أجهزة البصمة والوجه** | وارد | ZKTeco/Hikvision SDK أو ملفات | مزامنة دورية + معالجة الازدواج |
| **تتبع المركبات والمعدات GPS/IoT** | وارد | MQTT / REST | ساعات تشغيل، موقع، وقود، تنبيهات |
| **Primavera P6 / MS Project** | ثنائي | XER / XML / MPP | استيراد وتصدير الجداول والخطوط المرجعية |
| **BIM (Revit / Navisworks)** | وارد | IFC / BCF / Autodesk API | ربط عناصر النموذج بأكواد الكلفة (5D) |
| **GIS** | ثنائي | WMS/WFS، PostGIS | حدود المشاريع، الأراضي، المرافق |
| **بوابات الدفع** | ثنائي | REST + Webhooks | تحصيل أقساط عقارية ورسوم خدمة |
| **الرسائل والواتساب** | صادر | Twilio / Meta Cloud API | إشعارات وتنبيهات |
| **البريد** | ثنائي | SMTP / IMAP / Graph API | أرشفة المراسلات تلقائياً في نطاق المستندات |
| **التوقيع الإلكتروني** | ثنائي | DocuSign / محلي | العقود والاعتمادات |
| **بوابات حكومية** (تراخيص/عمالة/تأمينات) | ثنائي | حسب المتاح | قد يتطلب RPA حيث لا توجد API |
| **أنظمة المحاسبة القديمة** | وارد لمرة واحدة | ETL | الترحيل الافتتاحي |

### حوكمة التكامل
- كل موصّل خارجي **معزول خلف Anti-Corruption Layer** — تغيّر النظام الخارجي لا يلوث نموذج نطاقنا.
- **سجل تبادل كامل** (Request/Response) مع إخفاء الأسرار، محفوظ 90 يوماً.
- **قاطع الدائرة (Circuit Breaker)** + مهلات + إعادة محاولة تصاعدية + تنبيه عند التعطل.
- **Webhooks صادرة** موقّعة بـ HMAC للأنظمة التي تريد الاستماع لنا.
- **API عامة موثّقة** بـ OpenAPI 3.1 + بيئة تجريبية (Sandbox).

## قرارات مفتوحة

1. **ناقل الأحداث:** هل نبدأ بـ Postgres + BullMQ (بسيط، كافٍ حتى ~500 حدث/ثانية) أم NATS JetStream / Kafka من البداية؟ **توصيتي: Postgres Outbox + BullMQ في المرحلة 1–3، والانتقال لـ NATS عند الحاجة الفعلية.**
2. هل توجد أجهزة بصمة/GPS قائمة يجب دعمها تحديداً؟ الموديل يحدد جهد الموصّل.
3. هل مطلوب تكامل Primavera P6 فعلياً، أم محرك جدولة داخلي يكفي؟
