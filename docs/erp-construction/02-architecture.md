# 02 — المعمارية العامة

## 1. القرار المعماري الأساسي: Modular Monolith أولاً

**التوصية:** نبدأ بـ **مونوليث معياري (Modular Monolith)** مقسّم داخلياً إلى نطاقات محدودة (Bounded Contexts) بحدود صارمة، مع قابلية استخراج أي نطاق كخدمة مستقلة لاحقاً.

**لماذا لا خدمات مصغّرة من البداية؟**

| المعيار | Modular Monolith | Microservices من اليوم الأول |
|---------|------------------|------------------------------|
| اتساق البيانات المالية | معاملة قاعدة بيانات واحدة (ACID) — حرج للمحاسبة | Saga موزعة + اتساق نهائي = كوابيس تسوية |
| سرعة التطوير الأولى | عالية جداً | بطيئة (بنية تحتية قبل قيمة) |
| كلفة التشغيل | خادم واحد + قاعدة | 20 خدمة + service mesh + tracing |
| فريق مطلوب | 6–10 مطورين | 25+ مطور و DevOps مخصص |
| التتبع والتصحيح | مباشر | معقّد |

نظام ERP للمقاولات **قلبه معاملات مالية مترابطة**؛ تفكيكها مبكراً خطأ كلاسيكي. الاستخراج لاحقاً يكون منطقياً لثلاثة أشياء فقط: **معالجة المستندات/OCR**، **محرك التقارير والـ BI**، **بوابة الإشعارات والتكاملات الخارجية**.

## 2. الحدود الصارمة بين النطاقات (Module Boundaries)

قاعدة ذهبية تُفرض بأدوات آلية (ESLint boundaries + مراجعة معمارية):

1. **لا استعلام مباشر عبر النطاقات.** نطاق المشتريات لا يقرأ جداول الموارد البشرية مباشرة — يستدعي واجهتها العامة أو يستمع لأحداثها.
2. **كل نطاق يملك مخططه (Schema) الخاص** داخل نفس قاعدة البيانات (`procurement.*`, `finance.*`, `hcm.*`). العزل بالمخطط لا بالخادم.
3. **العقد بين النطاقات ثلاثة أنواع فقط:** واجهة خدمة عامة (Public Service Interface)، حدث نطاق (Domain Event)، عرض قراءة مادي (Read Model).
4. **لا مفاتيح أجنبية عابرة للنطاقات** إلا نحو النطاق المرجعي (MDM/Core) — لأن هذا يمنع الاستخراج المستقبلي.

## 4. تعدد المستأجرين (Multi-Tenancy)

**النموذج المقترح: مستأجر مشترك + عزل على مستوى الصف (Shared DB + RLS) مع خيار قاعدة مخصصة للعملاء الكبار.**

- كل جدول يحمل `tenant_id` + `entity_id` (الكيان القانوني).
- سياسات **PostgreSQL Row Level Security** تُفعّل على كل جدول: لا يمكن لاستعلام أن يتجاوز مستأجره حتى لو أخطأ المطور.
- `SET LOCAL app.tenant_id` يُضبط في بداية كل معاملة من طبقة الوسيط.
- العميل الكبير (>500 مستخدم أو متطلب سيادة بيانات) يُنقل إلى **قاعدة بيانات مخصصة** بنفس الكود — مسار ترقية جاهز.

**تحذير تصميمي:** RLS وحدها لا تكفي — تُضاف طبقة تحقق في التطبيق (Defense in Depth) لأن اتصالات المشرف (superuser) تتجاوز RLS افتراضياً.

## 5. مبادئ التصميم الحاكمة (10 مبادئ)

1. **مصدر حقيقة واحد لكل حقيقة.** لا يُخزَّن رقم الكلفة في مكانين — يُشتق أو يُنشر بحدث.
2. **كل حركة ذات أثر مالي تُرحَّل لحظياً** إلى دفتر الكلفة ودفتر الأستاذ، لا دفعة ليلية.
3. **المستندات غير قابلة للتعديل بعد الاعتماد** — التصحيح بمستند عكسي أو نسخة جديدة، لا تعديل صامت.
4. **كل شيء مؤرَّخ (Temporal).** الأسعار، الأسقف، الهياكل التنظيمية، أسعار الصرف — كلها بتاريخ سريان.
5. **الحذف ممنوع.** حذف منطقي (`deleted_at`) + سجل تدقيق كامل قبل/بعد.
6. **الأتمتة الافتراضية.** كل خطوة يدوية متكررة يجب أن يكون لها بديل مؤتمت أو مبرر مكتوب.
7. **العمل دون اتصال حق أساسي** لكل ما يُنجز في الموقع.
8. **API-First.** كل شاشة تستهلك واجهة موثّقة عامة — لا منطق مخفي في الواجهة.
9. **معرّف الطلب (Idempotency Key) إلزامي** على كل عملية كتابة — لأن الشبكات الميدانية تعيد الإرسال.
10. **الأداء ميزة وظيفية.** ميزانية أداء لكل شاشة تُختبر آلياً في CI.

## 6. أنماط معمارية مستخدمة

| النمط | أين يُستخدم | لماذا |
|-------|-------------|-------|
| **Domain Events + Outbox** | كل تكامل بين النطاقات | فصل + ضمان التسليم مرة واحدة على الأقل |
| **CQRS الخفيف** | التقارير والـ Dashboards | فصل قراءة ثقيلة عن كتابة معاملاتية |
| **Event Sourcing (انتقائي)** | دفتر الأستاذ، دفتر الكلفة، سجل التدقيق | لا يجوز فقدان تاريخ مالي |
| **Saga / Process Manager** | دورة الشراء، دورة المستخلص، دورة التوظيف | عمليات طويلة متعددة الأقسام |
| **Specification Pattern** | مصفوفة الاعتمادات، قواعد الصلاحيات | قواعد أعمال متغيرة بلا نشر كود |
| **Strategy Pattern** | تسعير المخزون، الاستهلاك، احتساب الإيراد | تعدد الطرق المحاسبية |
| **Materialized Views** | لوحات EVM، أرصدة المخزون، أعمار الديون | حسابات ثقيلة متكررة |
| **Sidecar Sync Engine** | تطبيق الجوال | مزامنة تفاضلية مع حل تعارضات |

## 7. مخطط النشر (Deployment Topology)

```
                    ┌─────────────┐
   المستخدمون  ───▶ │  CDN / WAF  │
                    └──────┬──────┘
                           ▼
                 ┌───────────────────┐
                 │   Load Balancer   │
                 └─────────┬─────────┘
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌───────────┐     ┌───────────┐     ┌──────────────┐
  │ Web (SSR) │     │  API x N  │     │ Worker Pool  │
  │  Next.js  │     │  NestJS   │     │ BullMQ Jobs  │
  └───────────┘     └─────┬─────┘     └──────┬───────┘
                          │                   │
      ┌───────────────────┼───────────────────┼──────────────┐
      ▼                   ▼                   ▼              ▼
┌───────────┐      ┌────────────┐      ┌───────────┐  ┌────────────┐
│PostgreSQL │      │   Redis    │      │ S3/MinIO  │  │ OpenSearch │
│ Primary   │      │ Cache+Queue│      │ Documents │  │  البحث     │
│  + Replica│      └────────────┘      └───────────┘  └────────────┘
└─────┬─────┘
      │ CDC / ETL
      ▼
┌──────────────────────────┐
│ مستودع البيانات (DWH)    │
│ ClickHouse + dbt + BI    │
└──────────────────────────┘
```

- **بيئات:** تطوير → اختبار → تدريب (بيانات مُقنّعة) → إنتاج.
- **النسخ الاحتياطي:** PITR كل 5 دقائق + نسخة يومية خارج المنطقة + اختبار استعادة شهري إلزامي.
- **RTO ≤ 1 ساعة، RPO ≤ 5 دقائق.**

## قرارات مفتوحة

- هل نستخدم **Supabase** (Postgres مُدار + Auth + Storage + Realtime) لتسريع الانطلاق، أم بنية مستقلة كاملة؟ توصيتي: Supabase للمرحلة 1–2 ثم تقييم، لأن RLS فيها أصلاً جوهر المنتج.
- هل مطلوب **نشر داخلي (On-Premise)** لبعض العملاء؟ يؤثر على اختيار الخدمات المُدارة.
