# 08 — الأداء والقياس

## 1. ميزانية الأداء (أهداف رقمية مُلزمة)

هذه ليست أمنيات — تُختبر آلياً في CI وتُراقب في الإنتاج، والتجاوز يكسر البناء.

| العملية | الهدف P50 | الهدف P95 | الحد الأقصى |
|---------|-----------|-----------|--------------|
| تحميل شاشة قائمة (50 سجل) | 200ms | 500ms | 1s |
| فتح مستند (مستخلص/أمر شراء) | 250ms | 600ms | 1.5s |
| حفظ مستند | 300ms | 800ms | 2s |
| بحث نصي عام | 200ms | 700ms | 2s |
| لوحة معلومات تنفيذية | 500ms | 1.5s | 3s |
| تقرير EVM لمشروع | 800ms | 2s | 5s |
| ترحيل دورة رواتب (1000 موظف) | — | 60s | 180s |
| مزامنة جوال تفاضلية | 1s | 4s | 15s |
| تصدير Excel (50,000 سطر) | — | 20s | 60s (غير متزامن) |
| First Contentful Paint (ويب) | 1s | 2s | 2.5s |

**قواعد صارمة:**
- أي عملية تتجاوز **10 ثوانٍ** تصبح **مهمة خلفية** مع إشعار عند الاكتمال — لا شاشة انتظار.
- أي شاشة تجلب > 200 سجل تستخدم **ترقيم بالمؤشر (Cursor Pagination)** — لا `OFFSET` أبداً على جداول كبيرة.
- **صفر استعلامات N+1** — يُفحص آلياً في الاختبارات.

## 2. استراتيجية قاعدة البيانات

### الفهرسة
- فهرس مركّب على كل جدول يبدأ بـ `(tenant_id, ...)` — لأن كل استعلام مُقيّد بالمستأجر.
- فهارس جزئية للحالات الشائعة: `WHERE deleted_at IS NULL AND status = 'ACTIVE'`.
- `GIN` على `JSONB` وعلى `pg_trgm` للبحث العربي التقريبي.
- `GiST` على PostGIS وعلى النطاقات الزمنية.
- **مراجعة دورية** لـ `pg_stat_statements` — أبطأ 20 استعلاماً تُعالج كل سبرنت.

### التقسيم (Partitioning)
| الجدول | مفتاح التقسيم | الفترة |
|--------|---------------|--------|
| `cost_ledger_entry` | `posting_date` | شهري |
| `journal_line` | `posting_date` | شهري |
| `audit_log` | `occurred_at` | شهري + أرشفة بعد 24 شهراً |
| `attendance` | `attendance_date` | سنوي |
| `notification` | `created_at` | شهري + حذف بعد 90 يوماً |
| `meter_reading` | `reading_at` | شهري |

### فصل الأحمال
```
كتابة/معاملات ──▶ Primary
قراءة تقارير  ──▶ Read Replica  (تأخر مقبول ≤ 5 ثوانٍ)
تحليلات ثقيلة ──▶ مستودع البيانات (ClickHouse)  — لا تلمس OLTP إطلاقاً
```

### العروض المادية (Materialized Views)
تُحدَّث بالحدث أو بجدولة، لا عند كل قراءة:
`project_cost_summary` · `wbs_rollup` · `stock_balance_by_warehouse` · `ar_aging` · `ap_aging` · `equipment_utilization` · `sla_compliance` · `unit_inventory_status` · `evm_snapshot`.

## 3. التخزين المؤقت (Caching)

| المستوى | ما يُخزَّن | مدة الصلاحية | آلية الإبطال |
|---------|-----------|--------------|--------------|
| CDN | الأصول الثابتة، الخطوط، الصور | سنة (بتوقيع الإصدار) | تغيير المسار |
| المتصفح | استعلامات TanStack Query | 30 ثانية – 5 دقائق | إعادة الجلب عند التركيز |
| Redis | البيانات المرجعية، الصلاحيات، الإعدادات، أسعار الصرف | 5–60 دقيقة | حدث `MasterDataChanged` |
| Redis | نتائج التقارير الثقيلة | 5–15 دقيقة | حدث ترحيل ذي صلة |
| التطبيق | مخططات التحقق، تعريفات سير العمل | حتى إعادة التشغيل | إعادة تحميل بإشارة |

**قاعدة:** لا تخزين مؤقت للأرصدة المالية اللحظية ولا للمخزون المتاح — دقتها تسبق سرعتها.

## 4. القابلية للتوسع (Scalability)

| البُعد | الاستراتيجية |
|--------|--------------|
| المستخدمون المتزامنون | توسّع أفقي لخوادم API (بلا حالة) خلف موازن حمل |
| حجم البيانات | تقسيم + أرشفة + مستودع بيانات منفصل |
| العمليات الثقيلة | فصلها إلى عمّال (Workers) بطوابير ذات أولويات |
| القراءات | نسخ قراءة + عروض مادية + تخزين مؤقت |
| الملفات | S3 + CDN — لا تمر عبر خوادم التطبيق |
| المستأجرون الكبار | ترحيلهم لقاعدة بيانات مخصصة بنفس الكود |

**نقاط الاختناق المتوقعة والحلول:**
| الاختناق | العلاج |
|----------|--------|
| الترقيم المتسلسل بلا فجوات | مولّد أرقام بقفل قصير جداً على جدول عدّاد منفصل |
| ترحيل الرواتب الشهري | معالجة مجمّعة (Batch) في نافذة منخفضة الحمل |
| إقفال نهاية الشهر | فترات محاسبية + ترحيل تدريجي لا دفعة واحدة |
| رفع مئات الصور من موقع | رفع مباشر إلى S3 بروابط موقّعة — لا يمر عبر API |
| لوحة تنفيذية على 200 مشروع | لقطات محسوبة مسبقاً (`evm_snapshot`) تُحدّث كل 15 دقيقة |

## 5. المراقبة والقياس (Observability)

**الأعمدة الثلاثة + الرابع:**
1. **مقاييس (Metrics)** — Prometheus: زمن الاستجابة، معدل الأخطاء، عمق الطوابير، اتصالات القاعدة.
2. **سجلات (Logs)** — Loki: منظّمة JSON، مع `correlation_id` في كل سطر.
3. **تتبّع (Traces)** — Tempo/OpenTelemetry: رحلة الطلب عبر الطبقات والأحداث.
4. **مقاييس الأعمال** — لوحة خاصة: عدد المستخلصات المعلقة، الأحداث في DLQ، الاعتمادات المتأخرة، فشل المزامنة.

**تنبيهات إلزامية:**
- ارتفاع P95 فوق الميزانية لمدة 5 دقائق.
- عمق طابور Outbox > 1000 أو تأخر > 60 ثانية.
- أي رسالة تصل DLQ.
- فشل نسخة احتياطية أو فشل اختبار استعادة.
- فشل مزامنة جهاز ميداني > 24 ساعة.
- فشل تكامل خارجي (فوترة إلكترونية، بنك) — تنبيه فوري.

**قواعد التسجيل:** لا تُسجَّل بيانات حساسة (رواتب، حسابات بنكية، رموز) — تُقنَّع آلياً.

## 6. الاختبار

| النوع | التغطية المستهدفة |
|-------|-------------------|
| اختبار وحدة | ≥ 80% للمنطق المالي والكلفوي، ≥ 60% عام |
| اختبار تكامل | كل Saga كاملة من البداية للنهاية |
| اختبار عقود (Contract Tests) | كل حدث نطاق وكل واجهة بين النطاقات |
| اختبار صلاحيات | مصفوفة (دور × مستند × إجراء) آلياً |
| اختبار حمل | k6 — سيناريو ذروة: 500 مستخدم متزامن، إقفال شهري، مزامنة 100 جهاز |
| اختبار مزامنة | محاكاة انقطاع، تعارض، إعادة إرسال |
| اختبار أمني | SAST + SCA + DAST في CI |
| اختبار قبول | سيناريوهات أعمال حقيقية مع المستخدمين قبل كل إصدار |

**اختبار مالي خاص:** مطابقة آلية بين **مجموع دفتر الكلفة** و**مجموع دفتر الأستاذ** بعد كل مجموعة اختبارات — أي انحراف يكسر البناء فوراً.
