# 13 — معمارية «قلب واحد وتطبيقات متعددة»

> هذه الوثيقة تُثبّت القرار المعماري النهائي وتُفصّل آلية بناء تطبيق بعد آخر.
> تُكمل الوثيقة 02 ولا تلغيها.

## 1. المعنيان المختلفان لعبارة «تطبيقات متعددة»

العبارة تحتمل تفسيرين متباعدين جداً في الأثر:

| | **أ — تطبيقات داخل نظام واحد** ✅ | **ب — تطبيقات منفصلة النشر** ❌ |
|---|---|---|
| النشر | خدمة واحدة تُنشر | ٨–١٥ خدمة تُنشر وتُراقب |
| قاعدة البيانات | واحدة، بمخطط لكل تطبيق | قاعدة لكل تطبيق |
| الاتساق المالي | معاملة واحدة ذرّية (ACID) | اتساق نهائي + تسويات يدوية |
| قراءة بيانات تطبيق آخر | استدعاء دالة معلنة | نداء شبكي قد يفشل |
| إضافة تطبيق جديد | مجلد جديد | خدمة + قاعدة + مراقبة + نشر |
| الفريق اللازم | ٢–٤ مطورين | ١٥+ مطوراً و DevOps متفرغ |
| التتبّع عند الخطأ | مباشر في مكان واحد | تتبّع موزّع عبر خدمات |

**القرار: (أ).** والسبب حاسم في حالتنا تحديداً:

قلب هذا النظام **دفتر كلفة ودفتر أستاذ**. حين يُصرف كيس إسمنت، يجب أن يحدث **في لحظة واحدة غير قابلة للتجزئة**:
نقص المخزون + قيد الكلفة على المشروع + القيد المحاسبي. إن كانت هذه في ثلاث قواعد بيانات منفصلة،
فأي انقطاع في المنتصف يترك النظام **غير متوازن**، وتصبح مطابقة الأرصدة عملاً يدوياً شهرياً.

هذا ليس رأياً معمارياً — هو السبب الذي يجعل أنظمة ERP الجادة تبقى موحّدة القاعدة حتى مع مئات المطورين.

## 2. ما هو «القلب» بالضبط

القلب **ليس** تطبيقاً ولا شاشة. هو ثمانية أشياء فقط، تُبنى مرة واحدة، ولا تُلمس بعدها إلا نادراً:

| # | مكوّن القلب | ما يملكه |
|---|-------------|----------|
| ١ | **الهوية والصلاحيات** | من أنت · ماذا تستطيع · في أي مشروع · حتى أي سقف |
| ٢ | **الهيكل التنظيمي** | الشركة · الفروع · الأقسام · مراكز التكلفة · **المشاريع** |
| ٣ | **البيانات المرجعية** | الشركاء · الأصناف · دليل الحسابات · أكواد الكلفة · العملات وأسعار الصرف · الضرائب |
| ٤ | **دفتر الكلفة ودفتر الأستاذ** | السجل المالي الوحيد — كل التطبيقات تكتب فيه ولا يكتب هو في أحد |
| ٥ | **محرك سير العمل** | الاعتمادات · مصفوفة الصلاحيات · اللجان متعددة الموقّعين · التصعيد |
| ٦ | **المستندات والطباعة** | الملفات · المرفقات · القوالب · إنتاج PDF مطابق للأصل |
| ٧ | **ناقل الأحداث** | الصندوق الصادر · التسليم المضمون · الاشتراكات |
| ٨ | **سجل التدقيق والترقيم** | من غيّر ماذا ومتى · سلاسل الترقيم المستندي |

### القاعدة الحاكمة الوحيدة

> **القلب لا يعرف بوجود أي تطبيق.**
> التطبيقات تستورد من القلب. القلب لا يستورد من أي تطبيق. صفر استثناءات.

هذه القاعدة هي **كل** ما يجعل «تطبيق بعد الآخر» ممكناً فعلياً. لحظة أن يعرف القلب بتطبيق معيّن،
يصبح كل تطبيق جديد يكسر ما قبله، وتنهار الفكرة كلها.

### تحذير: القلب لا يُبنى بالتدريج

الإغراء الطبيعي هو بناء جزء من القلب مع كل تطبيق. **لا تفعل.**
إضافة دفتر الكلفة أو نظام الصلاحيات إلى خمسة تطبيقات قائمة عمل شاق ومؤلم.

**القلب يُبنى أولاً وكاملاً تقريباً: ٦–٨ أسابيع.** ثم تتوالى التطبيقات بسرعة كبيرة.
هذه الأسابيع الثمانية لا تُنتج شاشة يراها المستخدم — وهي أفضل استثمار في المشروع كله.

## 3. تصحيح مهم: التطبيق يُقسَّم بالبيانات لا بالقسم الإداري

قولك «كل تطبيق يختص بقسم» صحيح في الروح، لكن التطبيق الحرفي له فخّ:

**الأقسام الإدارية تتغيّر — البيانات لا تتغيّر.**

مثال واقعي: «قسم الحسابات» عندك قد يتولى دفتر الأستاذ **و** كشف الرواتب **و** متابعة التحصيل.
لو بنينا «تطبيق قسم الحسابات» لجمعنا ثلاثة نطاقات بيانات مختلفة في صندوق واحد.
وحين تُعاد هيكلة الأقسام بعد سنتين، يصبح التطبيق بلا معنى.

**القاعدة الصحيحة:** التطبيق يملك **مستنداً وبياناته**، ثم يُمنح كل قسم التطبيقات التي يحتاجها.

| بدل | نبني |
|-----|------|
| «تطبيق قسم الحسابات» | تطبيق **الدفعات** + تطبيق **الأجور** + تطبيق **النقد** |
| «تطبيق قسم المشاريع» | تطبيق **العقود** + تطبيق **الذرعات** |

قسم الحسابات يفتح ثلاثة تطبيقات؛ مدير المشروع يفتح اثنين؛ كلٌّ يرى ما يخصه — بلا ازدواج بيانات.

### اختبار صحة الحدود

> إذا احتاج التطبيق (أ) بيانات التطبيق (ب) عبر **أكثر من ٢–٣ دوالّ معلنة**،
> فالحدّ في المكان الخطأ. **ادمج التطبيقين** بدل بناء جسر معقّد بينهما.

الحدود الصحيحة تُعرف بقلّة الكلام بين الجانبين، لا بجماله.

التطبيق السابق ويعطون ملاحظات بينما يُبنى اللاحق.

**كل تطبيق يُسلَّم للاستخدام الفعلي فور اكتماله** — لا انتظار لاكتمال النظام.

## 5. الربط بين التطبيقات — ثلاثة أنماط مسموحة وواحد ممنوع

### ✅ النمط الأول: القراءة من القلب (الأكثر استخداماً — ٨٠٪ من الحالات)

كل تطبيق يقرأ من القلب مباشرة: المشاريع، الشركاء، الأصناف، الحسابات، أكواد الكلفة، الصلاحيات.
**لا يحتاج إذناً ولا وسيطاً** — القلب مِلك الجميع.

معظم ما يبدو «ربطاً بين تطبيقين» هو في الحقيقة **قراءة مشتركة من القلب**.

### ✅ النمط الثاني: واجهة معلنة (للسؤال الفوري)

حين يحتاج تطبيق جواباً **الآن** ليتخذ قراراً:

```
تطبيق المواد ──▶ payments.getCertifiedProgress(projectId)
تطبيق الدفعات ──▶ materials.getStockEntryForms(projectId, period)
```

كل تطبيق يعرض ملفاً واحداً باسم `public.ts` فيه دوالّه المعلنة. **لا شيء خارج هذا الملف يُستورد من الخارج.**

### ✅ النمط الثالث: حدث (للأثر غير الفوري)

```
تطبيق الدفعات ينشر:  PaymentCertified { projectId, amount, retention, taxWithheld }
   ├─▶ القلب: قيد في دفتر الأستاذ وذمة مدينة
   ├─▶ تطبيق النقد: تحديث توقع التدفق
   └─▶ الغلاف: إشعار للمدير المالي
```

الناشر **لا يعرف من يستمع**. إضافة مستمع جديد لا تلمس الناشر إطلاقاً.

### ❌ الممنوع الوحيد: قراءة جداول تطبيق آخر مباشرة

```sql
-- ممنوع منعاً باتاً
SELECT * FROM payments.measurement_lines WHERE ...   -- من داخل تطبيق المواد
```

هذا هو **بالضبط** ما يحوّل «تطبيقات مستقلة» إلى كتلة متشابكة خلال ستة أشهر،
ويجعل أي تعديل في تطبيق يكسر ثلاثة تطبيقات أخرى بصمت.

**يُفرَض آلياً**، لا بالانضباط الشخصي:
- كل تطبيق بمخطط قاعدة بيانات باسمه: `contracts.*` · `payments.*` · `treasury.*`
- **لا مفاتيح أجنبية عابرة بين مخططات التطبيقات** — فقط نحو `core.*`
- فحص في التكامل المستمر يرفض أي استيراد يتجاوز `public.ts`
- مراجعة الكود ترفض أي استعلام يذكر مخطط تطبيق آخر


### تسجيل التطبيق — هكذا يصبح «إضافة تطبيق» عملاً بلا مخاطر

```ts
// apps/contracts/app.config.ts
{
  id: 'contracts',
  nameAr: 'العقود',
  menu: [
    { path: '/contracts',            labelAr: 'العقود' },
    { path: '/contracts/boq',        labelAr: 'الكشف المسعّر' },
    { path: '/contracts/variations', labelAr: 'أوامر الغيار' },
  ],
  permissions: ['contract.view', 'contract.create', 'contract.approve'],
  dashboardWidgets: ['activeContracts', 'ldRiskAlert'],
  dependsOn: ['core'],
  licenseKey: 'contracts',          // ← للتفعيل التجاري لاحقاً
}
```

الغلاف يقرأ هذا الملف ويبني القائمة والصلاحيات واللوحات تلقائياً.
**إضافة تطبيق = مجلد جديد + سطر تسجيل. ولا سطر واحد يتغيّر في القلب أو في التطبيقات القائمة.**

## 7. لماذا تخدم هذه البنية هدفك التجاري

قرارك السادس كان: «لشركتي أولاً، ثم قد يُعرض للشركات الأخرى». هذه البنية تخدمه مباشرة:

| القدرة | كيف تتحقق |
|--------|-----------|
| **بيع بالباقات** | شركة صيانة صغيرة تشتري تطبيقين؛ مقاول كبير يشتري ثمانية — بنفس الكود |
| **التفعيل بالترخيص** | `licenseKey` في تعريف كل تطبيق — التفعيل إعداد لا نشر |
| **تسعير متدرّج** | سعر لكل تطبيق مفعّل لكل مستأجر |
| **تخصيص لعميل** | تطبيق خاص بعميل واحد دون المساس بالبقية |
| **خطوط الأعمال الأخرى** | التطوير العقاري والصيانة والاستشارات = تطبيقات تُضاف فوق القلب نفسه |
| **عرض تجريبي** | تفعيل تطبيق واحد للعميل المحتمل ليجرّبه |

## 8. ما يُنشر فعلاً (نقطة تُخلط كثيراً)

«نظام واحد» لا يعني «برنامج واحد يعمل». تُنشر **أربع وحدات تشغيلية** حتى في أصغر إعداد:

| الوحدة | لماذا منفصلة |
|--------|--------------|
| **الويب** | تُخدَّم من شبكة توصيل، وتُحدَّث بلا مساس بالخادم |
| **الـ API** | تحمل كل التطبيقات والقلب — تتوسّع أفقياً بلا حالة |
| **العامل الخلفي (Worker)** | المهام الثقيلة: الطباعة · التقارير · المزامنة · الأحداث — لا تُبطئ المستخدم |
| **تطبيق الجوال** | تطبيق مستقل فعلاً، يعمل دون اتصال ويزامن مع الـ API |

هذا **ليس** خدمات مصغّرة — إنه نظام واحد بأربع عمليات تشغيل. الفرق أن الأربعة يشاركون
**نفس الكود ونفس قاعدة البيانات ونفس المعاملات**.

---

## 9. متى نفصل تطبيقاً إلى خدمة مستقلة فعلاً

ثلاثة أسباب مشروعة فقط — وليس منها «يبدو أنظف»:

1. **الفريق تجاوز ١٥–٢٠ مطوراً** ويتزاحمون على نفس الكود.
2. **نمط حمل مختلف جذرياً**: معالجة الصور، التقارير الثقيلة، استقبال بيانات أجهزة التتبّع.
3. **متطلب عزل أمني**: بوابة خارجية للموردين أو العملاء يجب ألا تلمس قاعدة العمليات.

**والبنية أعلاه تجعل هذا الفصل سهلاً حين يحين وقته** — لأن التطبيق أصلاً معزول بمخططه وواجهته المعلنة.
نستخرجه بلا إعادة كتابة. **هذا هو جوهر الفكرة: نؤجّل التعقيد ولا نمنعه.**

## 10. الخلاصة

| السؤال | الجواب |
|--------|--------|
| قلب واحد وتطبيقات متعددة؟ | ✅ **نعم — وهذا هو القرار المعتمد** |
| تطبيقات منفصلة النشر؟ | ❌ لا — ليس بفريق ٢–٣ أشخاص، وليس مع دفتر كلفة في القلب |
| نُكمل تطبيقاً ثم ننتقل للتالي؟ | ✅ نعم — بتداخل أسبوع أو اثنين، وتسليم كل تطبيق فور اكتماله |
| نقسّم بالقسم الإداري؟ | ⚠️ لا — نقسّم **بالمستند والبيانات**، ثم نمنح كل قسم تطبيقاته |
| كيف يقرأ تطبيق بيانات آخر؟ | من القلب · أو بدالّة معلنة · أو بحدث — **وممنوع SQL مباشر** |
| هل نبني القلب بالتدريج؟ | ❌ لا — **يُبنى أولاً وكاملاً في ٦–٨ أسابيع** |
