# 07 — الأمان والحوكمة

## 1. نموذج الصلاحيات: ليس RBAC وحده

نظام المقاولات لا تكفيه الأدوار. الصلاحية الحقيقية معادلة من خمسة عناصر:

```
السماح = f( الدور ، النطاق التنظيمي ، نوع المستند ، حالة المستند ، السقف المالي )
```

**مثال واقعي:**
> "مدير المشروع" يستطيع **اعتماد** طلب شراء بحالة "مقدَّم" بقيمة حتى **50,000 د.ع** في **مشاريعه المسندة له فقط** — ولا يستطيع رؤية رواتب فريقه.

### الطبقات الأربع
1. **RBAC** — الدور يعطي مجموعة صلاحيات أساسية.
2. **ABAC** — سمات (المشروع، الفرع، الكيان القانوني، القيمة) تقيّد الصلاحية.
3. **أمن على مستوى الصف (RLS)** — تُفرض في قاعدة البيانات، لا في الكود فقط.
4. **أمن على مستوى الحقل** — حقول حساسة (الراتب، هامش الربح، سعر التكلفة) مخفية أو مقنّعة حسب الدور.

### تنفيذ RLS
```sql
ALTER TABLE project.projects ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON project.projects
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

CREATE POLICY project_scope ON project.projects
  USING (
    current_setting('app.is_admin')::boolean
    OR id IN (SELECT project_id FROM core.user_project_access
              WHERE user_id = current_setting('app.user_id')::uuid)
  );
```
> **دفاع بالعمق:** RLS + تحقق في طبقة التطبيق + اختبارات صلاحيات آلية في CI. الاعتماد على طبقة واحدة خطأ.

## 2. الهوية والمصادقة

- **OIDC / OAuth 2.1** — Keycloak أو Supabase Auth أو Auth0.
- **MFA إلزامي** لأدوار: المالية، الموارد البشرية، مدراء النظام، معتمدو المبالغ الكبيرة.
- **SSO مؤسسي** (SAML/OIDC) للربط مع Microsoft Entra ID.
- **رموز قصيرة الأجل** (Access 15 دقيقة) + Refresh Token دوّار (Rotating) مع كشف إعادة الاستخدام.
- **إدارة الجلسات والأجهزة**: عرض الأجهزة النشطة، إنهاء عن بُعد، ربط الجوال بجهاز واحد.
- **سياسة كلمات المرور** + فحص التسريبات + قفل بعد محاولات فاشلة.
- **حسابات الخدمة** منفصلة عن حسابات البشر، بمفاتيح API محدودة النطاق وقابلة للتدوير.

## 3. حماية البيانات

| الطبقة | الإجراء |
|--------|---------|
| **أثناء النقل** | TLS 1.3 إلزامي، HSTS، تثبيت الشهادات في تطبيق الجوال |
| **أثناء التخزين** | تشفير القرص (AES-256) + تشفير على مستوى الحقل للبيانات فائقة الحساسية |
| **حقول مشفّرة** | الرواتب، أرقام الحسابات البنكية، الوثائق الشخصية، هوامش الربح، أسعار التكلفة، بيانات المناقصات قبل الفتح |
| **إخفاء الهوية** | بيئات الاختبار والتدريب تستخدم بيانات مُقنّعة إلزامياً |
| **الملفات** | فحص فيروسات عند الرفع، روابط موقّعة قصيرة الأجل، منع التنفيذ |
| **الأسرار** | Vault / Secrets Manager — لا أسرار في الكود أو متغيرات بيئة عارية |
| **الاحتفاظ والحذف** | سياسة احتفاظ لكل نوع بيانات + حذف آمن عند انتهاء المدة القانونية |

## 4. سجل التدقيق (Audit Trail)

**غير قابل للتعديل، بلا استثناء.**

```
AuditLog: id, tenant_id, occurred_at, actor_id, actor_ip, user_agent,
          entity_type, entity_id, action (CREATE|UPDATE|DELETE|APPROVE|REJECT|
          POST|REVERSE|EXPORT|VIEW_SENSITIVE),
          before_json, after_json, changed_fields[],
          correlation_id, reason (إلزامي للإجراءات الحساسة),
          hash, prev_hash   ← سلسلة تجزئة لكشف أي عبث
```

- **سلسلة التجزئة (Hash Chain):** كل سجل يحتوي تجزئة السجل السابق — أي حذف أو تعديل يكسر السلسلة ويُكتشف.
- **يُسجَّل أيضاً:** كل تصدير بيانات، كل عرض لبيانات حساسة، كل تسجيل دخول ناجح وفاشل، كل تغيير صلاحية.
- **لا أحد يستطيع الحذف** — بما فيهم مدير النظام. التخزين في جدول للإضافة فقط + نسخ فورية إلى تخزين غير قابل للتغيير (WORM).

## 5. الفصل بين المهام (Segregation of Duties)

النظام يفرض قواعد SoD آلياً ويمنع التعارضات:

| التعارض الممنوع | السبب |
|-----------------|-------|
| من ينشئ المورّد ≠ من يعتمد أمر الشراء | منع موردين وهميين |
| من يستلم البضاعة ≠ من يعتمد الفاتورة | منع فواتير بلا توريد |
| من يُدخل الموظف ≠ من يعتمد الراتب | منع موظفين وهميين |
| من يُعد المستخلص ≠ من يعتمده | منع مبالغة الكميات |
| من يجرد المخزون ≠ أمين المخزن | منع تغطية العجز |
| من يُنشئ القيد ≠ من يرحّله | ضبط محاسبي أساسي |

**شاشة تحليل SoD** تعرض المستخدمين الذين يجمعون صلاحيات متعارضة — تقرير أساسي لأي مدقق.

## 6. الاعتمادات ومصفوفة الصلاحيات المالية (DoA)

```
ApprovalMatrix:
  doc_type, legal_entity, project_type, cost_center,
  amount_from, amount_to, currency,
  level_1_role, level_2_role, level_3_role,
  requires_all | requires_any,
  escalation_hours, delegate_on_absence, valid_from, valid_to
```
- **بيانات لا كود** — التعديل من الشاشة بلا نشر برمجي، مع سجل تغييرات.
- **التفويض في الغياب** إلزامي: لا مستند يعلق لأن مديراً في إجازة.
- **التصعيد الزمني** التلقائي عند تجاوز المهلة.
- **الاعتماد بالتوقيع الإلكتروني** مع تسجيل IP والجهاز.

## 7. أمن التطبيق (AppSec)

- منع حقن SQL بالكامل عبر استعلامات معلمة (ORM) — لا تركيب نصوص.
- تحقق من المدخلات بـ Zod على كل حدود (API، جوال، استيراد ملفات).
- حماية CSRF، رؤوس أمنية (CSP، X-Frame-Options، Referrer-Policy).
- **تحديد المعدل (Rate Limiting)** لكل مستخدم/IP/نقطة نهاية.
- منع التصدير الجماعي غير المبرر (تنبيه عند تصدير > 10,000 سجل).
- فحص التبعيات (SCA) + فحص الكود الساكن (SAST) في CI + **اختبار اختراق سنوي**.
- مكافأة اكتشاف الثغرات إن كان النظام يواجه الإنترنت العام.
- **بوابات خارجية معزولة**: بوابة المورّد/العميل تعمل بخدمة منفصلة وصلاحيات دنيا (Least Privilege) — لا تصل لقاعدة العمليات مباشرة.

## 8. استمرارية الأعمال

| المقياس | الهدف |
|---------|-------|
| RTO (زمن الاستعادة) | ≤ 1 ساعة |
| RPO (فقدان البيانات المقبول) | ≤ 5 دقائق |
| اختبار الاستعادة | شهري إلزامي وموثّق |
| نسخة خارج المنطقة | يومية |
| خطة الطوارئ | موثّقة ومُختبرة سنوياً (Disaster Recovery Drill) |

## 9. الامتثال

- **ISO 27001** — إطار أمن المعلومات (النظام يُصمَّم متوافقاً حتى لو لم نشهد فوراً).
- **ISO 9001 / 45001 / 14001** — نطاقات الجودة والسلامة والبيئة مبنية لتوليد أدلة التدقيق تلقائياً.
- **قوانين حماية البيانات المحلية** — حق الاطلاع، التصحيح، سيادة البيانات (استضافة داخل الدولة إن لزم).
- **المتطلبات الضريبية** — الفوترة الإلكترونية، تسلسل الفواتير، الاحتفاظ بالسجلات 5–10 سنوات.

## قرارات مفتوحة

1. أين تُستضاف البيانات؟ (سيادة البيانات قد تفرض استضافة محلية)
2. هل مطلوب شهادة ISO 27001 فعلياً، أم التوافق كافٍ؟
3. هل هناك متطلب لتوقيع رقمي معتمد من جهة حكومية؟
