# 06 — التقنيات المقترحة (Technology Stack)

## المبدأ الحاكم في الاختيار

اخترنا تقنيات **ناضجة، مملوكة لمجتمع واسع، بلغة واحدة عبر الطبقات** — لأن أكبر خطر على مشروع ERP ليس التقنية بل **قدرة الفريق على الصيانة بعد 5 سنوات**. لغة واحدة (TypeScript) عبر الخادم والويب والجوال تعني: نموذج مشترك، تحقق مشترك، ومطور واحد يعمل في كل الطبقات.

---

## 1. الخادم (Backend)

| المكوّن | الاختيار | المبرر | البديل |
|---------|----------|--------|--------|
| اللغة | **TypeScript (Node.js 22 LTS)** | نفس لغة الواجهة، نظام أنواع قوي، سوق مطورين واسع | C# / .NET 9 (أقوى في المعاملات المالية، أضعف في مشاركة الكود) |
| الإطار | **NestJS 11** | معماري بطبيعته (Modules/DI)، يفرض الحدود التي نريدها، توثيق ممتاز | Fastify + بنية يدوية |
| ORM | **Drizzle ORM** (أو Prisma) | SQL شفاف، هجرات صريحة، أداء عالٍ — مهم لاستعلامات مالية معقدة | TypeORM (لا يُنصح) |
| التحقق | **Zod** | مخطط واحد يُستخدم في الخادم والواجهة والجوال | class-validator |
| المهام والطوابير | **BullMQ على Redis** | جدولة، إعادة محاولة، أولويات، لوحة مراقبة جاهزة | Temporal (أقوى للـ Sagas، أثقل) |
| محرك سير العمل | **مبني داخلياً على نموذج حالات + BullMQ** | متطلباتنا خاصة (مصفوفة اعتمادات ديناميكية) | Camunda 8 (قوي، ثقيل ترخيصاً) |
| محرك القواعد | **json-rules-engine** أو تعبيرات CEL | القواعد بيانات لا كود — تتغير بلا نشر | — |
| الملفات | **S3 API (AWS S3 / MinIO / Supabase Storage)** | معياري وقابل للنقل | — |
| التقارير | **Puppeteer/Chromium لـ PDF + ExcelJS** | دقة عالية في العربي RTL | Carbone / JasperReports |

## 2. قاعدة البيانات

| المكوّن | الاختيار | الغرض |
|---------|----------|-------|
| **PostgreSQL 17** | القاعدة الأساسية | معاملات ACID، RLS، JSONB، امتدادات غنية |
| `ltree` | شجرة WBS ودليل الحسابات والمواقع | استعلامات الشجرة الفورية |
| `PostGIS` | مواقع المشاريع، حدود الأراضي، تتبع الفنيين | تحليل مكاني |
| `pg_partman` | تقسيم الجداول الضخمة | أداء الجداول الزمنية |
| `pgcrypto` | تشفير الحقول الحساسة | الرواتب، الوثائق الشخصية |
| `pg_trgm` | بحث نصي تقريبي عربي | البحث في الأسماء والأصناف |
| **Redis 7** | تخزين مؤقت + طوابير + جلسات + أقفال موزّعة | الأداء |
| **OpenSearch** | بحث نصي كامل في المستندات وOCR | البحث المؤسسي |
| **ClickHouse** (المرحلة 4+) | مستودع التحليلات | تقارير على مئات الملايين من الأسطر بثوانٍ |

> **ملاحظة على Supabase:** إذا اخترنا Supabase فهي تعطينا Postgres مُدارة + Auth + Storage + Realtime + RLS جاهزة، وتختصر 2–3 أشهر من عمل البنية التحتية. القيد: تحكّم أقل في التخصيص العميق. **توصيتي: نعم للمرحلة 1–3، مع كتابة الكود بحيث لا يرتبط بها (Postgres قياسي).**

## 3. الواجهة (Frontend)

| المكوّن | الاختيار | المبرر |
|---------|----------|--------|
| الإطار | **Next.js 15 (App Router) + React 19** | عرض من الخادم للسرعة، تقسيم الحزم، بيئة ناضجة |
| اللغة | TypeScript | مشاركة الأنواع مع الخادم |
| التنسيق | **Tailwind CSS 4** مع دعم منطقي للاتجاه (logical properties) | RTL/LTR بنفس الكود دون تكرار |
| المكوّنات | **shadcn/ui + Radix** | ملكية الكود، إتاحة (a11y) مدمجة، تخصيص كامل |
| حالة الخادم | **TanStack Query** | تخزين مؤقت، إعادة جلب، تحديث متفائل |
| النماذج | **React Hook Form + Zod** | نماذج ضخمة (مستخلص فيه 40 حقلاً) بأداء عالٍ |
| الجداول | **TanStack Table** + تمرير افتراضي | جداول بعشرات آلاف الأسطر |
| الرسوم البيانية | **Recharts** أو ECharts | لوحات المعلومات ومنحنى S |
| الجدول الزمني | **مكوّن Gantt مخصص (SVG/Canvas)** أو DHTMLX | Gantt تفاعلي بآلاف الأنشطة |
| التدويل | **next-intl** | عربي/إنجليزي/كردي، تواريخ هجرية وميلادية |
| التصميم | نظام تصميم موحّد + رموز | اتساق عبر 27 نطاقاً |

**قرار حاسم: العربية أولاً (RTL-first).** الاتجاه ليس ميزة مضافة بل أساس التصميم — الأرقام، التواريخ، الجداول المالية (المدين/الدائن)، اتجاه الأسهم في الرسوم.

## 4. الجوال (Mobile / Field App)

| المكوّن | الاختيار | المبرر |
|---------|----------|--------|
| الإطار | **React Native (Expo)** | مشاركة المنطق والأنواع مع الويب، فريق واحد | البديل: Flutter (أداء رسومي أفضل، فريق منفصل) |
| القاعدة المحلية | **WatermelonDB** أو SQLite + Drizzle | محرك مزامنة مبني للـ offline |
| الوسائط | ضغط صور، رفع مستأنف | شبكات ضعيفة |
| القدرات | كاميرا، GPS، QR/Barcode، توقيع، بصمة، إشعارات دفع، وضع خارج الخدمة | متطلبات الميدان |

**تطبيقان منفصلان مقترحان:**
1. **تطبيق الموقع** — للمهندسين والمشرفين وأمناء المخازن (تقارير، مواد، فحص، سلامة).
2. **تطبيق الخدمة الذاتية** — للموظفين (حضور، إجازات، قسيمة راتب، اعتمادات).
> تطبيق ثالث اختياري لفنيي الصيانة إن كان خط FM محورياً.

## 6. الذكاء الاصطناعي (طبقة اختيارية لكن عالية العائد)

| الاستخدام | التقنية | القيمة |
|-----------|---------|--------|
| استخراج بيانات الفواتير والمستندات | نموذج لغوي متعدد الوسائط + OCR | إدخال آلي بدل يدوي |
| تصنيف المراسلات وربطها بالمطالبات | تصنيف نصي | لا تضيع مطالبة |
| تنبؤ تأخير المشروع | انحدار على بيانات التقدم التاريخية | إنذار مبكر |
| تنبؤ تجاوز الكلفة (EAC ذكي) | سلاسل زمنية | دقة توقع أعلى من الخطي |
| كشف الشذوذ في المشتريات والصرف | كشف شذوذ | مكافحة الاحتيال |
| تحليل صور السلامة (PPE) | رؤية حاسوبية | امتثال تلقائي |
| مساعد محادثة على بيانات الشركة | RAG على مستودع البيانات | "كم صرفنا على الحديد هذا الشهر؟" |
| تقدير أولي من BOQ تاريخي | استرجاع + تشابه | تسريع التسعير |

**قاعدة حاكمة:** الذكاء الاصطناعي **يقترح ولا يقرر**. كل مخرج يمر باعتماد بشري ويُسجَّل في سجل التدقيق.

## 7. مصفوفة القرار: لماذا لا الأنظمة الجاهزة؟

| البديل | الميزة | لماذا لا يكفي |
|--------|--------|----------------|
| SAP / Oracle | نضج كامل | كلفة ضخمة، تخصيص مؤلم، غير ملائم للسوق المحلي والعربية |
| Odoo | مفتوح وسريع | وحدات المقاولات ضعيفة (لا EVM، لا مستخلصات، لا مطالبات) — تخصيصه أصعب من البناء |
| Procore / Aconex | ممتاز للمشاريع | لا مالية ولا موارد بشرية ولا تطوير عقاري |
| أنظمة محلية | ملائمة لغوياً | معمارية قديمة، لا API، لا جوال، لا قابلية توسع |

**الخلاصة:** لا يوجد نظام واحد يغطي المقاولات + التطوير العقاري + الصيانة + الاستشارات بالعربية بمعمارية حديثة. هذه فجوة سوقية حقيقية.
